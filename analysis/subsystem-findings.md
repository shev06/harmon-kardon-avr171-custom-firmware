# AVR1710 firmware reverse-engineering notes

These are static-analysis findings for the unmodified 6 MiB firmware image. Ghidra's function boundaries and decompiler output are heuristic; no firmware has been flashed.

## Image and coverage

- Imported as one initialized executable/writable ARM Cortex little-endian block, `0x08000000–0x085fffff`.
- A read-only Ghidra P-code CPU emulation started at reset handler `0x0800d36c` with vector-table SP `0x20009188`. The reset routine walks the descriptor table at `0x0800d134–0x0800d158`: the first entry calls `0x080030ee` with count `0x7180` and destination `0x20000008`, clearing through `0x20007184`; the second calls `0x08002fe2`, copying eight bytes from `0x0800d50c` to `0x20000000` (emulated words `8, 8`). The walk completes at step 29,126, with both boundary words in the cleared range verified as zero. Startup then calls `FUN_08005500`; its first initializer (`FUN_0800595c`) calls `FUN_080081b0`, which configures clock registers and waits for RCC-ready bits. Since the emulator has no MMIO model, the zero-valued/uninitialized RCC status leads to a non-returning failure loop at `0x080082a0`, reached at step 45,818. This explains the emulation stop; it is not evidence that the actual receiver hangs. Initial general registers were not hardware-captured and Ghidra reports an uninitialized `r8` read, so this remains CPU-only startup analysis, not a complete boot or USB-update emulation.
- **Independently cross-validated with a second, unrelated emulator (QEMU) — see dedicated section below.** A full ARM toolchain (`arm-none-eabi-gcc`/`gdb`) and `qemu-system-arm` (STM32F405-class `netduinoplus2`/`olimex-stm32-h405` machine models) were set up specifically to re-run this same boot trace with real modeled peripherals instead of Ghidra's no-MMIO P-code interpreter. QEMU, executing from the same true reset vector, halts at the **exact same address** (`0x080082a0`) — a strong, independent confirmation that this stall is a genuine property of the firmware's control flow and not an artifact of Ghidra's emulation limitations specifically.

## CONFIRMED (via QEMU emulation + static disassembly): exact clock-init wait/timeout logic at 0x080081b0–0x080082a4

Toolchain: `arm-none-eabi-gcc`/`binutils`/`gdb` (16.2.0/2.47/18.1) + `qemu-system-arm` 11.1.3, installed via Homebrew specifically for this validation (see `../emulation-build/README.md` for the full environment, build commands, and reproduction steps). The real 6 MiB `.fw` is loaded **read-only** into QEMU's emulated RAM via `-device loader,file=...,addr=0x08000000` (QEMU's `-kernel` option refuses raw/non-ELF files on this machine type); the loader's `cpu-num=0` property was found to set PC directly to the load address rather than performing a true vector-table reset fetch (SP, however, *was* correctly picked up from the real vector table, reading back as `0x20009188` exactly as expected) — worked around by manually setting `$pc` to the real reset vector (`0x0800d36c`) over the GDB remote protocol before continuing. This is purely an emulation/debugging workaround; nothing is written to the real firmware file or any physical device.

Static disassembly (`arm-none-eabi-objdump -D -b binary -M force-thumb`, saved at `clock-init-static-disasm.log`) of `0x080081b0`–`0x080082a4`, confirmed live by QEMU actually executing it from reset, fully resolves the previously-vague "waits for RCC-ready bits" into exact bit-level logic — this is the function Ghidra's call trace identified as `FUN_080081b0`:

1. **RCC de-init** (`0x080081b2`–`0x080081e6`): sets `RCC_CR` bit 0 (HSION), zeroes `RCC_CFGR` entirely (selects HSI, clears all prescalers), clears `RCC_CR` bits {0,3,8} via a literal mask, zeroes `RCC_CIR` (clock interrupt flags), clears `RCC_CR` bit 18 (HSEBYP — i.e. expects a real crystal, not an external clock input), zeroes one more flag word — a textbook `RCC_DeInit()`-style reset to known-good defaults before reconfiguring.
2. **HSE enable + bounded poll** (`0x080081f8`–`0x08008238`): sets `RCC_CR` bit 16 (HSEON), then polls `RCC_CR` bit 17 (HSERDY) in a loop with an **explicit, counted timeout of 1280 iterations** (`cmp r0, #0x500`). If HSERDY becomes 1 within that budget, proceeds to step 3. **If the timeout is reached without HSERDY ever being set, execution falls straight through to the permanent halt trap at `0x080082a0`** (`bne 0x080082a0` at `0x08008238`) — a `b.n` to itself, with no further register checks, i.e. a deliberate, unrecoverable "give up" trap on HSE failure.
3. **Prescaler bits + PLL enable + unbounded poll** (`0x800823a`–`0x8008272`): sets `RCC_CFGR` bits 15 and [12,10] (RTC/APB prescaler-related), writes a literal into a second register (likely `RCC_PLLCFGR`), sets `RCC_CR` bit 24 (PLLON), then polls `RCC_CR` bit 25 (PLLRDY) in a loop with **no timeout at all** — an unconditional infinite wait if the PLL never locks.
4. **Flash wait-states + clock switch + unbounded poll** (`0x8008274`–`0x80082a4`): writes `3` into a byte register (consistent with `FLASH_ACR` latency = 3 wait states, appropriate for a ~100+ MHz core clock), clears then sets `RCC_CFGR` bits [1:0] (`SW` field) to select PLL as the system clock, then polls `RCC_CFGR` bits [3:2] (`SWS`, clock-switch-status) for value `0b10` (PLL confirmed active) — again **no timeout**; success falls through to a clean `bx lr` return at `0x80082a4`.

**Why both emulators stall at exactly the same spot**: neither Ghidra's P-code interpreter (no MMIO model at all) nor QEMU's STM32F405 peripheral model simulates real HSE crystal stabilization — `RCC_CR` bit 17 (HSERDY) never becomes 1 in either tool, so the bounded 1280-iteration timeout in step 2 always elapses and both land on the same halt trap. **This is a known limitation of both emulation approaches, not evidence of a real hardware fault** — confirmed by directly reading back `RCC_CR`/`RCC_CFGR` in QEMU (both stayed at their RCC_DeInit defaults, e.g. `RCC_CR = 0x00010001` = HSION+HSEON set but HSERDY never appearing). Attempting to patch these registers to "ready" values *after* the CPU already reached `0x080082a0` had no effect (confirmed by testing) — the trap is a one-way, unconditional branch-to-self with no re-check, so any fix must patch memory *before* the 1280-iteration timeout elapses (e.g. break at the function entry `0x080081b0` and patch immediately), which was not completed this session (GDB software breakpoints silently failed to insert into the emulated flash region — likely modeled read-only — so a hardware breakpoint, `hbreak`, would be needed instead, left as a clear next step if resumed).
- **Practical significance**: this result is a genuine, independent cross-check of the reverse-engineering work — two differently-implemented emulators, run via completely different mechanisms (static P-code interpretation vs. full QEMU system emulation), agree exactly on both the address and (now) the precise bit-level reason for a control-flow stall in the very first few thousand instructions of boot. It does not, by itself, tell us anything new about the *application* region, the USB/FAT update path, or the BCO orchestrator — those all execute much later and were not reached by this trace — but it meaningfully increases confidence in the overall static-analysis methodology used throughout this project, and leaves a reusable, documented QEMU+GDB environment (`../emulation-build/`) for continuing this specific thread (getting past clock-init to observe later boot stages) in a future session.
- Clock setup uses literal MMIO addresses `0x40023800` (RCC CR), `0x40023804` (RCC PLLCFGR), `0x40023808` (RCC CFGR), and `0x40023c00` (FLASH ACR). The PLLCFGR literal `0x25403c19` decodes to M=25, N=240, P=2, HSE source, Q=5; if the board's HSE is 25 MHz, this implies a 120 MHz system clock and 48 MHz PLLQ clock. The HSE frequency is not established by this firmware image. The address map is consistent with STM32F4-family peripherals and narrows the likely MCU family, but does not identify the exact part.
- Ghidra identified 3,028 functions totaling 613,186 function bytes and 1,817 strings (1,667 referenced). This is an analysis inventory, not proof every function or data region is classified.
- The current scan has not established independently loadable images or a verified partition map.
- A new read-only 64 KiB area pass finds nearly all Ghidra functions in `0x08000000–0x0809ffff`, with a small additional code/UI area at `0x080b0000–0x080cffff`; no functions were identified beyond that. This is an address-density map, not a component/partition proof. The file offsets are addresses minus `0x08000000`.
- The 256 KiB range `0x080d0000–0x080fffff` and 1 MiB range `0x08400000–0x084fffff` are each entirely `0xff` by byte count, consistent with padding/erased flash. Other `0xff`-heavy gaps occur around the data-bearing regions. Ghidra/REA do not establish whether those gaps are intentional slots or format padding.
- Unclassified data at `0x08100000` and later is not empty: the image contains repeated `iYEtLANA` markers and four `Cirrus Logic, Inc.` strings at `0x08100503`, `0x081126bf`, `0x08129297`, and nearby clusters, plus structured numeric tables around file offsets `0x00200000`, `0x00300000`, and `0x00500000`. This supports a hypothesis of embedded audio/DSP-related payload or tables, but no code references or format parser has established component boundaries, load addresses, or executability. Binwalk/Unblob likewise did not extract a verified component.
- Raw byte search finds eight `iYEtLANA` occurrences (file offsets 695,512; 715,892; 731,476; 1,172,832; 1,193,456; 1,209,376; 2,870,404; and 3,192,000). Their repeated local byte patterns suggest structured records/payloads, not ordinary text. No public GitHub code/repository match for this marker or AVR1710 firmware was found in the focused search.
- The Cortex-M vector table gives initial SP `0x20009188` and reset pointer `0x0800d36d`. After the table walk, the reset path calls `FUN_08005500`, whose main loop does not return under the decompiled control flow; a later call to `0x0800d1a2` appears to be a return/failure trap rather than a normal next boot stage. Repeated interrupt-vector targets at `0x0800d3a4` onward point into identical `ff f7 fe bf` byte patterns, consistent with branch-to-self stubs, but this has not been validated on hardware.
- A vector-table scan found a genuine second Cortex-M application table at `0x08010000`: initial SP `0x2001d300`, reset vector `0x080c6f2d`, exception handlers at `0x080b97c8` onward, and peripheral handlers beginning at `0x080c7f3c`. The reset trampoline calls `0x0808bb98` (the STM32F4-style clock initializer) then branches to `0x080c7579`. `FUN_0808bb98` directly references this vector-table base, providing strong evidence that the file packages a second application/boot context rather than merely containing table-like data. Its exact component role and load/selection logic remain unresolved; the `0x080c7578` decompilation is currently unreliable because Ghidra has not cleanly separated code and data in that area.
- **Resolved**: the literal pool for `FUN_0808bb98` was read directly (`0x0808bcac`=`0xe000ed08` = Cortex-M `SCB->VTOR`, `0x0808bcb0`=`0x08010000`). The function de-inits RCC, re-runs HSE/PLL/flash-latency setup (`FUN_0808bbdc`), then sets `SCB->VTOR = 0x08010000` and returns (a plain `bx lr`, not a jump). Its three call sites (`0x080657ba`, `0x080724ba`, and the `0x08010000` table's own reset trampoline `0x080c6f2c`) are all physically located **above** `0x08010000`, i.e. inside the same large `0x08010000+` code area. This is the standard CMSIS `SystemInit()` idiom of an application asserting its own vector-table base — it is **self-referential**, not proof of a bootloader-to-application handoff.

## Confirmed: 0x08000000–0x0800d378 is a complete, independent USB firmware-update bootloader

This is the central new finding of this session and directly answers the long-standing "where is the flash writer / update validator" question.

- **Region boundary.** Of the image's defined functions, 174 have entry points below `0x08010000` (packed into `0x08000000–0x0800d378`, then `0xff`-padded out to the 64 KiB boundary); 2,655 have entry points at/above `0x08010000`. A complete **raw-instruction** cross-reference scan (not limited to pre-existing Function boundaries, which left real code ungrouped — see below) over `0x08000000–0x0800ffff` vs `0x08010000–0x080cffff` found **zero direct code references in either direction**. Any hand-off between this bootloader and the `0x08010000+` application (if one exists) is therefore either an indirect/computed branch that static analysis cannot resolve, or the two images are independently entered (e.g. by a hardware/option-byte boot selection) rather than calling one another. This supersedes the earlier "second embedded image" framing: the two regions are code-isolated from each other.
- **Important analysis-coverage gap found and worked around:** large stretches of real code in this low region (e.g. `0x08006800–0x08006b00`, `0x08007700–0x080079f0`, `0x0800ad6a–0x0800b270`) are already disassembled (`InstructionDB`) but were never grouped into `Function` objects by the prior analysis pass, so `getFunctionContaining()`/`getReferencesTo()` silently report "no function"/"no references" there. Raw instruction iteration and raw little-endian word scanning (not Ghidra's reference manager) were required to read this code; keep using that approach for this region rather than trusting function-based queries alone.
- **It is a USB-drive-based updater using ST's USBH (USB Host) middleware.** Strings `"USBH_STM32UH_TRANSFER"` (`0x0800d158`) and `"USBH_TIMO"` (truncated `USBH_TIMEOUT`, `0x0800d348`) are classic ST USBH middleware debug strings (unreferenced in this Release build, consistent with stripped debug logging, not evidence of being unused code).
- **OSD progress/status strings**, reconstructed into their pointer table at `0x08008030–0x08008058` (read by code at `0x08007816–0x080078f2`, itself not Function-wrapped): `"LOADING:    "` (`0x0800d2b8`), `"MCU    UPDATE   "` (`0x0800d1c8`), `"BCO    UPDATE   "` (`0x0800d1dc`), `"WRITE:    "` (`0x0800d318`), `"SOFTWARE UPDATE  "` (`0x0800d1f0`/`0x0800d218` two variants), `"PLEASE WAIT...   "` (`0x0800d204`/`0x0800d22c` two variants), plus `"SYSTEM UPDATE   "`, `"USB DETECT...   "`, `"WRITE:    00%   "`, `"WRITE:   FAIL   "` nearby in the same string block (`0x0800d254–0x0800d290`). `"MCU"` vs `"BCO"` as distinct update targets indicates this bootloader updates **at least two separate components** (this MCU's own flash, and a second "BCO" board/controller, likely reached over a separate link).
- **Confirmed, complete STM32F4 Standard-Peripheral-Library-style flash driver**, all in the low region, all verified by direct disassembly:
  - `FUN_0800af06` — `FLASH_GetStatus()` equivalent: reads FLASH_SR literal pool slot `0x0800af50`, decodes BSY (bit16)→1, PGPERR (bit4)→5, other error bits (mask `0xef`)→6, else→8 (OK).
  - `FUN_0800af54` (+ spin-delay helper `FUN_0800af86`) — `FLASH_WaitForLastOperation()` equivalent: polls `FUN_0800af06` with a caller-supplied retry count, returns 9 on timeout.
  - `FUN_0800ada4` — `FLASH_Unlock()` equivalent: writes STM32F4 key sequence (literal pool `0x0800af44`/`0x0800af48`) to `FLASH_KEYR` (`0x40023c04`, pool slot `0x0800af40`).
  - `FUN_0800adba` — `FLASH_Lock()` equivalent: sets `FLASH_CR` (`0x40023c10`, pool slot `0x0800af4c`) bit 31 (LOCK).
  - `FUN_0800adcc` — `FLASH_EraseSector()` equivalent: sets the sector-number field + SER (bit1) in `FLASH_CR`, sets STRT (bit16), polls completion, clears SER/sector field.
  - `FUN_0800ae4a` — `FLASH_ProgramWord()` equivalent: sets PSIZE=10b (32-bit) + PG (bit0) in `FLASH_CR`, performs `str data,[address]` directly to the flash address passed in by the caller, polls completion, clears PG.
  - `FUN_0800aeaa` — a sibling program routine using `strb` (byte-sized writes) instead of `str`, i.e. `FLASH_ProgramByte()`-equivalent.
  - `FLASH_SR` literal pool slot is `0x0800af50`; all five literal-pool slots sit contiguously at `0x0800af40–0x0800af50` and were read directly from the image (not just decompiled) to confirm the VTOR and FLASH register addresses used here.
  - Callers of these primitives cluster in two separate address ranges: `~0x08005d00–0x08006300` (candidate "MCU update" orchestrator — this chip's own internal flash) and `~0x08007800–0x08008100` (candidate "BCO update" orchestrator).
- **`"!!ANAM SOFT!!"` string** (`0x0800d2d8`) — **corrected finding, superseding an initial hash/signature hypothesis**: `FUN_0800aa9e` (called at `0x08005d7c` with this string as its path argument) is proven, via full decompilation of its callee chain (`func_0x08004c78`), to be a real **FAT-filesystem `fopen()`-style call**: classic C mode-string parsing (`"r"`, `"r+"`, `"w"`, `"w+"`, `"a"`, `"a+"`) plus genuine directory lookup, cluster-chain, and file-handle-table logic (`FUN_08003242` path-parse, `FUN_080010a4` directory lookup, `func_0x08003672` handle allocation, `FUN_08003f42`/`FUN_08003cc0` directory-entry read, `FUN_080015fe`/`FUN_080013e4` cluster-chain walk). The returned handle is cached at RAM `0x200070d0` and **is reused later as the stream read in the write loop below** — so `"!!ANAM SOFT!!"` is the internal path/alias the bootloader's VFS layer uses for the update data source (most likely an internal fixed alias the USB/FAT layer binds to whatever update file it found, rather than a literal required filename — the official instructions only mention placing the extracted archive contents at the USB root, with no mention of a required special filename).
  - Gating logic confirmed by disassembly: open-failure (handle `==0`) calls an error handler (`FUN_0800aa78`) and only halts in an infinite OSD-fail loop if a second, unrelated status byte (`*0x08005e60`) is also zero; open-success (handle `!=0`) checks a separate flag (`*0x08006934`) before calling `FLASH_Unlock`.

## CONFIRMED: exact flash target — STM32F4 sectors 4–11 (0x08010000–0x080fffff), bootloader sectors 0–3 are protected

This is the single most important confirmed fact of the whole investigation: **hard evidence, not inference, for exactly which flash range "MCU update" erases and reprograms.**

- The write loop is a state machine driven by a single state byte at RAM `0x08006a5c` (states 0–8), reached from the same orchestrator as the `fopen()` gate above. Raw disassembly of `0x08005ea0–0x080061e0` (state0 through state5) was decompiled/disassembled directly (not just inferred from callers).
- **State0** (`0x08005ea0`): initializes the sector index byte at RAM `0x08006b64` to **4** (not 0!), looks up `table[4]` from a sector-offset table, adds `0x08000000`, and stores it as the active flash write pointer (`0x08006b68`).
- **State1** (`0x08005f54`): calls `FLASH_EraseSector` (`0x0800adcc`) on the current sector.
- **State2** (`0x08005f8c`): calls `FUN_0800aaca` — a confirmed **`fread()`-equivalent** (signature matches `fread(ptr, size=1, nmemb=4, stream=cached_handle)`), reading up to 4 bytes from the opened stream into a local buffer, caching the byte count actually read.
- **State3** (`0x08005fd0`): if exactly 4 bytes were read, treats the buffer as one 32-bit word and calls `FLASH_ProgramWord` (`0x0800ae4a`); otherwise programs the remaining 0–3 bytes individually via `FLASH_ProgramByte` (`0x0800aeaa`). **Every write is immediately read back and compared**; any mismatch sets an error bit and jumps to an error state (5). On success, advances the flash pointer and two running byte counters by the number of bytes just written, and moves to state4.
- **State4** (`0x080060bc`): compares the running byte counter against a target length; if the current sector isn't full yet, loops back to state2 to read/write more. If the sector is full, advances the sector index (capped at **12**) and looks up the next sector's start address from the same table, looping back to state1 to erase the next sector — or, once the index reaches 12, sets state6 (done) and clears the busy flag.
- **Sector tables read directly from the flash image** (not decompiled — raw `od` bytes, pool slots `0x08006ba0`→`0x0800d0a8` and `0x08006ba4`→`0x0800d0dc`):
  - Offsets (×4-byte, 12 entries): `0x00000, 0x04000, 0x08000, 0x0c000, 0x10000, 0x20000, 0x40000, 0x60000, 0x80000, 0xa0000, 0xc0000, 0xe0000`
  - Sizes: `0x4000 ×4, 0x10000 ×1, 0x20000 ×7` → i.e. four 16 KiB + one 64 KiB + seven 128 KiB sectors — **the exact, textbook STM32F4 1 MiB flash sector map** (e.g. STM32F407/417-class parts).
  - This independently confirms the MCU family/flash size (1 MiB internal flash) with hard data, not just PLL-literal inference.
- **Conclusion**: starting the sector index at 4 means the write loop **begins at sector 4, whose table offset is `0x10000` → absolute address `0x08010000`** — exactly the previously-found second vector-table/application boundary. Sectors 0–3 (`0x08000000–0x0800ffff`, the 64 KiB bootloader region) are **never erased or programmed by this path** — the bootloader protects itself by construction (it simply never iterates over its own sectors), not via an explicit address-range check. The update therefore erases and reprograms sectors 4–11, i.e. `0x08010000–0x080fffff` (960 KiB), which is entirely consistent with — and now proves — the earlier "zero code cross-references between low/high regions" finding: there is no code jump between bootloader and app; the relationship is "bootloader erases-and-overwrites the app's flash sectors," which static code-reference analysis cannot detect by design.
- **Also resolves the 6 MiB image mystery**: since the MCU's own internal flash is only 1 MiB (`0x08000000–0x080fffff`), the remaining ~5 MiB of the dumped image (`0x08100000` onward, containing the `iYEtLANA`/Cirrus Logic markers found earlier) is **outside this MCU's internal flash address space entirely** — almost certainly a separate external (SPI/QSPI/parallel) flash device for DSP/audio data, addressed and loaded through a completely different mechanism not touched by this update path.
- **Practical implication:** this is now a hard, verified picture of the flash write mechanics (states, addresses, sector table, verify-after-write behavior). Still open: (1) how the USB/FAT layer selects/binds a specific file on the USB stick to the `"!!ANAM SOFT!!"` stream alias (i.e. what filename/pattern the user must actually provide), (2) whether any whole-file header/length/CRC check gates the process *before* state0 begins (the only integrity check confirmed so far is the per-word immediate readback-verify, which is a write-correctness check, not necessarily a content-authenticity check), and (3) the exact file layout expected — i.e. whether the update file is simply the raw bytes that belong at `0x08010000` onward with no header (plausible, given this full firmware image's own `0x08010000` region already contains exactly that data) or has a short header first. Error-state (5) behavior (OSD "WRITE: FAIL") is confirmed; no automatic recovery/re-flash routine has been found if a write fails partway through a sector.
- **Practical implication:** a genuine, working flash-programming path now has hard evidence (not just UI strings), and the `fopen()` discovery confirms a real embedded FAT driver is present and reachable from this bootloader. What is still missing before any custom image could be safely built for this path: (1) the exact USB file/header format the real update-file read loop expects, (2) any content-level checksum/signature validation of the actual update file (not yet found; the per-word readback-verify is the only confirmed integrity check), and (3) recovery behavior on a failed write (only the `"WRITE:   FAIL"` OSD string is confirmed so far; no confirmed recovery routine). Item (3) is also the key practical gate for attempting a real flash: without a confirmed in-firmware recovery path, a hardware-level recovery option (e.g. SWD/JTAG test points on the PCB) is the only safety net, and that has not been investigated (it requires physically inspecting the board, not firmware analysis).

## CONFIRMED: the real pre-write-loop orchestrator (states 1→2→3) — closes the "!!ANAM SOFT!!" binding question, confirms FLASH_Unlock, finds the detection-failure path

Raw-disassembly trace (`file-setup-trace.log`) of `0x08005d0a–0x08005e72`, the previously-unexplored gap between the thin entry stub `FUN_08005c00` and the already-documented write-loop switch at `0x08005e72`. Helper functions it calls were then decompiled directly (`file-helper-decompile.log`). This is a **different, higher-level state machine** than the sector write-loop (states 0–8 at RAM `0x08006a5c`) — it uses its own state byte at RAM `0x080069c8` with states 0–3, and **state 3 is what starts the sector write-loop** (confirming the two state machines are sequential stages of one overall update, not independent).

- **State 1** (`0x08005d22`): calls `FUN_0800aa52(1)`. Decompiled, this is an "acquire-slot → do-work → release-slot" wrapper around `func_0x08002e60` (scans a fixed array of 284-byte stream-table structs — matches the earlier-found 3-slot handle table exactly) and a real worker `func_0x0800167c(slot, 1)` — i.e. **"open stream slot #1."** Returns a distinct error code (`0x25`) if no free slot exists. On success (non-zero), the tick does nothing further (handle now live). On failure (0), it zeroes the handle variable (RAM `0x080069cc` — confirmed to be the same handle later dereferenced throughout the sector write-loop) and two flag bytes, then **advances the orchestrator state to 2**.
- **State 2** (`0x08005d56`): first writes the raw bytes `'f'`, `'w'` into a small buffer — near-certain evidence the real file match is **extension-based (`*.fw`)**, not a fixed exact filename (consistent with, and now explaining the mechanism behind, the OEM instructions' "just unzip it, no renaming" behavior). It then conditionally calls `FUN_0800aa9e("!!ANAM SOFT!!", &local_struct)` — **the literal string `"!!ANAM SOFT!!"` lives at flash address `0x0800d2d8`, confirmed by direct byte read of the firmware file.** This is the exact moment the internal alias gets bound to a real resolved file/stream, closing out open-work item 1 end-to-end: a file matching the extension pattern is found on the USB FAT volume, then resolved-by-name through this alias and stored as the active handle. A second conditional resolve attempt (different name pointer, from RAM `0x08006930`) follows, suggesting a fallback/alternate-name path exists (not yet further resolved). If the resulting handle is non-zero (success) and a second flag is set, it **sets the orchestrator state to 3**, conditionally calls `FUN_0800ada4` (see below), then explicitly resets the sector-write-loop's own state byte (`0x08006a5c`) to 0 — i.e. **this is the exact instant the sector write-loop is armed to start on the next tick.**
- **`FUN_0800ada4` is confirmed to be `FLASH_Unlock()`, not a file-seek call** (an earlier hypothesis, now ruled out): it writes two hard-coded 32-bit constants, `0x45670123` then `0xCDEF89AB`, through a pointer whose target — read directly from the image — is `0x40023C04`. Both the address and the two constants are an **exact, byte-for-byte match for the STM32F4 reference manual's documented `FLASH_KEYR` unlock-key sequence** (KEY1/KEY2), independent further confirmation of the STM32F4 silicon family. It is only called when a value read from `0x080069d4` (itself holding `0x40023C10` = `FLASH_CR`) is negative, i.e. **only when `FLASH_CR` bit 31 (the LOCK bit) is still set** — textbook "unlock flash only if currently locked" guard logic, run once, immediately before the sector write-loop is armed.
- **Detection-failure path** (handle still 0 after both resolve attempts, `0x08005de4` onward): calls `FUN_0800aa78(handle)` (the same acquire/work/release pattern, worker = `func_0x08002580` — almost certainly the matching **close/release** counterpart to state 1's open), then — if a further flag isn't already set — draws two OSD elements at different screen coordinates (two calls to a text/label routine, `FUN_08006d78`, with different literal x/y/len arguments), calls a six-times-repeated tick/flush routine, calls one more function, and then **enters a true infinite loop (unconditional branch-to-self)**. This is almost certainly the real "no update file found on USB stick" on-screen message and halt — i.e. the firmware's own answer to "what if there's no valid `.fw` file" is a clean, deliberate halt with an error shown, not a crash. This is a reassuring data point for the safety question (a missing/non-matching file is handled gracefully), but it does **not** tell us what happens if a file *is* found and matched but is then malformed/corrupt partway through the write-loop — that remains governed only by the previously-confirmed per-word readback-verify → error-state(5) path.
- **Correction / negative result**: the `0x08007800–0x08008100` window, previously only hypothesized (never confirmed) to be a "BCO update orchestrator," was raw-disassembled this round and does **not** match update/flash-programming code at all — it compares small fixed byte codes (`0x21/0x22/0x23/0x26/0x22`) against a 3-byte status/event record at `0x08007e18`, calls a probable OSD-draw routine (`0x0800650e`) repeatedly with small literal arguments, and runs a millisecond-counter modulo-5000 check — this pattern is far more consistent with a **remote-control/IR or front-panel keypress dispatcher driving periodic OSD updates** than any firmware-update logic. The real "BCO update" code path (if `"BCO"` even refers to a second update target rather than, e.g., a chip/module name encountered only in strings) has **not** been located; this old hypothesis should be treated as falsified rather than just "not yet confirmed."

**Net effect on the open-work list**: item 1 (how a USB file gets bound to `"!!ANAM SOFT!!"`) is now fully closed (extension-match + named-alias resolve, both addresses and the alias string confirmed). Item 2 (file-seek/header-skip for the untrimmed 6 MiB file) is still open — the one promising lead this round (`FUN_0800ada4`) turned out to be `FLASH_Unlock`, not a seek, so the actual seek/offset-skip mechanism remains unlocated. Item 4 (BCO path) regresses from "not yet traced" to "known wrong location, real location still unknown."

## Real embedded FAT driver confirmed (`FUN_08004c78`); file-seek question downgraded to "diminishing returns via static analysis"

Decompiled the two remaining un-examined helpers from the state 1/2 trace above (`file-open-worker-decompile.log`):

- **`FUN_0800167c`** (state 1's "open slot 1"): validates a small integer slot index (0 or 1 only) against a pre-existing table at `DAT_08001eb8` (stride `0x1da4` = 7588 bytes/entry) and binds it into the caller's handle struct. No path/filename or USB/FAT access of any kind — this is a **system-internal stream** (e.g. a console/UART-style stream), confirmed unrelated to the actual update file. It is a red herring with respect to the update file itself, but closes out what state 1 is for.
- **`FUN_08004c78`** (the real worker behind the `"!!ANAM SOFT!!"` resolve call): a genuine, fairly complete **embedded FAT-filesystem `fopen()`** — it parses a C-style mode string (`"r"`, `"r+"`, `"w"`, `"w+"`, `"a"`, `"a+"`, converted to a numeric mode 1–6 with the exact same branching stdio uses), performs real directory-entry lookup (`FUN_08003242`), reads/parses a FAT boot sector (`FUN_08003f14`/`FUN_08003ef4`), walks the FAT cluster chain (`FUN_080015fe`, `FUN_080013e4`), and populates a large (~877-byte) `FILE`-like struct with over a dozen distinct fields (cluster pointers, size, attributes, cache state). This is hard confirmation that a real, capable FAT driver underlies the whole update mechanism — not a minimal/toy reader.
- **Neither function contains an explicit seek/offset-skip call.** This leaves the `0x10000`-byte header-skip question (open-work item 2) genuinely unresolved: either a separate `fseek()`-equivalent call exists somewhere between the successful open and the write-loop's first `fread()` (not yet located), or the skip is encoded less directly (e.g. via one of the many unidentified fields in the ~877-byte FILE struct, or the FAT driver's own internal cluster-walk start point). Fully resolving this would mean tracing deep into this FAT library's dozen-plus internal sub-functions — **diminishing returns relative to the question's actual importance**, especially compared to confirming it empirically (e.g. attaching a real/emulated FAT-formatted USB disk under QEMU and observing the actual byte offset of the first flash-programmed word) if this is ever revisited.

## CONFIRMED: file-seek mechanism (closes item 2), full write-loop completion sequence states 6–8, and the bootloader→application jump trampoline (major finding — substantially resolves item 5)

A combined Ghidra pass (`AVRFinalSweep.java`/`final-sweep.log`) plus a smaller confirmatory follow-up (`AVRFinalSweep2.java`/`final-sweep2.log`) closed out the file-seek question and uncovered the complete post-write shutdown/handoff sequence, including a previously-unknown bootloader→application jump routine.

**File-seek mechanism — item 2 CONFIRMED CLOSED.** The init block (State0, `0x08005ea0`) calls `FUN_0800ab00(handle, 0, 0)` immediately followed by `FUN_0800ab00(handle, 0x10000, 1)`. A full decompile of `FUN_0800ab00` (`final-sweep2.log`) proves it really is `fseek()`: it acquires/validates the stream slot (`FUN_08002e60`), calls `FUN_08002c58(handle, offset, whence, ...)` — the genuine low-level seek — then releases the slot (`FUN_08002efc`); on acquire-failure it returns error code `0x25` (same error-code family already seen on the file-open path). So the two calls are exactly `fseek(handle, 0, SEEK_SET)` (rewind) followed by `fseek(handle, 0x10000, SEEK_CUR)` (skip forward 0x10000 bytes) — confirming the bootloader explicitly skips the first 64 KiB of the untrimmed 6 MiB OEM `.fw` file before its first `fread()`. The skip amount (`0x10000`) is read from the **same per-sector offset table** (`0x0800d0a8`, sector-4 entry) that also supplies the flash write address — read once *with* `+0x08000000` (the absolute flash pointer) and once *without* (the raw file offset). One table elegantly serves both purposes: file offset `X` always corresponds to flash address `0x08000000 + X`, for every sector, not just sector 4. This fully explains why the real device can be handed the complete, untrimmed, undocumented 6 MiB image with no separate header/length field.

**Write-loop states 6–8, fully decoded** (continuing on from the existing State4→"state6 (done)" transition documented above):
- **State6** (`0x0800625c`, cleanup): clears the busy flag, closes the file stream, then calls three helper functions that reset internal driver state — `FUN_08006554` (zeroes three small buffer/table regions: 32 bytes, two 5-byte arrays, and 16 bytes, then writes `4` and `8` into the two bytes immediately following the 16-byte block — a generic "reset stream/descriptor table to idle" pattern) and `FUN_080065c4` (calls four more sub-helpers, `0x08006758`/`0x08006774`/`0x080068d4`/`0x080068a2`, not further decompiled — plausible peripheral/driver shutdown). Advances to State7.
- **State7** (`0x080062b6`): sets the outer orchestrator's own state to 4, runs a short (~6-unit) software delay loop, calls `FUN_080062f0` (the jump trampoline, decoded below), then **unconditionally** enters an infinite self-loop (`b 0x080062e2`) regardless of whether the trampoline actually jumped anywhere.
- **State8**: no distinct code — falls to the shared idle/no-op tail (`pop {r0,r4,r5,pc}`).

**Major new discovery — `FUN_080062f0`, the bootloader→application jump trampoline.** Resolved entirely via direct byte-reads of its literal pool: it reads the application's own stored initial stack pointer from flash address `0x08010000` (the app's own vector-table slot 0), masks it with `0x2ffe0000`, and checks the result equals `0x20000000` (i.e. "does this look like a plausible internal-SRAM address?"). **If the check fails, the function just returns** (and State7's own code then falls into its unconditional infinite loop — a safe, deterministic hang, not a crash). **If the check passes**, it reads the app's own reset vector from `0x08010004`, executes `msr msp, <app_sp>` to switch the stack pointer, then `blx <app_reset_vector>` — a genuine software warm-jump/chainload into the freshly-written application. This is almost certainly the real mechanism underlying the OEM instructions' "auto power off / auto power on / UPGRADE SUCCESS" description: it is a **software jump performed by the bootloader itself, not a literal mains power-cycle** (any literal power-supply/relay cycling, if the hardware does that at all, would be driven by the newly-launched application's own startup code, not by this bootloader).
- **This trampoline is reused far more broadly than just the post-update path.** A caller search found **6 distinct call sites across 5 different functions** — not just the write-loop's own State7. One caller (`FUN_08005e6c`) is the write-loop function itself (State7, as expected), but the other five (`FUN_0800563a`, `FUN_08005be4`, `FUN_08005d5c`, and `FUN_08007ac4` — the last calling it twice from two different points) are distinct, previously-unexamined functions, almost certainly including the bootloader's **normal, non-update cold-boot path** ("no update file found/requested → just boot the existing application"). This means **every single path into the application — whether a plain cold boot or a post-update handoff — goes through the identical SP-sanity-validated jump.** A corrupted or partially-written app region can never be blindly executed from any entry point; the worst case anywhere is a safe, deterministic hang (requiring the user to retry via USB), never undefined/crash behavior. Critically, **none of this logic ever touches bootloader sectors 0–3** — the bootloader itself is always intact and always re-runs this same check on the next power-up, regardless of what state the application region was left in.
- This also fully explains the earlier "zero static LOW→HIGH code cross-references" finding (`boot-app-boundary-v3.log`): the only connection between bootloader and app is this runtime-computed `blx <register>`, which is invisible to static cross-reference analysis by construction — not evidence the regions are unrelated, just evidence the link is a computed jump rather than a fixed call target.
- **Net effect on item 5 (recovery/resume path)**: no persisted "update was in progress" marker exists anywhere (all write-loop state lives in ordinary volatile SRAM, confirmed in an earlier pass), so there is no automatic resume-after-power-loss. However, the firmware's own defensive design means this matters less than it would otherwise: any interrupted/corrupted update simply results in the SP-sanity check failing on the next boot attempt, which safely hangs rather than crashing, and the bootloader (sectors 0–3) is categorically never at risk from this code path. The practical recovery story is therefore "safe, deterministic hang on bad app flash, requiring a human to retry the USB-update procedure" — not "silent brick" and not "automatic self-healing" — with no additional in-firmware resume capability beyond that.

## CONFIRMED: the bootloader unconditionally re-scans for a USB update file on every single cold boot, fully independent of application state (closes item 5's last open question, substantially de-risks item 10)

Triggered by the user's direct question ("i thought since bootloader is seperate to app its quite safe") — decompiled all 4 of the previously-unexamined non-write-loop callers of the jump trampoline (`AVRBootRecoveryTrace.java`/`boot-recovery-trace.log`) to determine whether USB-update-mode is bootloader-driven (independent of the app) or requires the app's own running menu.

- **`FUN_0800ad6a`** (the gating check) is a 10-byte function that does one thing: `ldr r0,[0x50000440]` — a **direct read of a raw STM32 USB-peripheral hardware register** (address `0x50000440`, within the STM32F4's USB OTG_FS peripheral block at `0x50000000`). This has zero dependency on any application code or state — it is pure bootloader-resident hardware polling.
- **`FUN_08005be4`** polls this register every loop iteration. If no USB device is sensed for a sustained `0x3ffff` (262,143) consecutive polls, it gives up waiting and falls through to the normal boot-the-app jump (`FUN_080062f0`, SP-sanity-gated, then hang if invalid). If a device **is** sensed and stays sensed for 1000 consecutive polls (debounce), it marks the connection confirmed and calls `FUN_08005d0a` — the **same pre-write-loop orchestrator entry point already fully traced above** (states 1→2→3: `*.fw` extension match, `resolve("!!ANAM SOFT!!", ...)`, `FLASH_Unlock`).
- **`FUN_08005d5c`** (orchestrator state 2, called from `FUN_08005d0a`) attempts the file resolve/open; if it fails (no valid `*.fw` found on the stick), it **also** falls through to the identical normal boot-the-app jump. Only on a successful resolve does it advance into the real sector-4–11 write loop.
- **`FUN_0800563a`** (a sibling check, independent call chain) is a separate remote-control/key-code polling loop (compares captured codes against fixed values `'Q'`/`'R'`/`0x10`/`0x01`) that can also force entry into update-adjacent state after repeated detections, or times out after 10 iterations and falls through to the same boot-the-app jump.
- **`FUN_08007ac4`** is a third, independent handshake/state machine (possibly input-device or the "BCO" path) with its own timeout and success paths — both of which **also** terminate in the identical boot-the-app jump pattern.
- **All 4 of these functions, and everything they call, live entirely within the bootloader's own address range (well below `0x08010000`)** — none of them read, require, or depend on anything in the application region. They constitute the bootloader's own self-contained main-loop/superloop, run on every single reset **before** the SP-sanity-gated jump into the application is ever attempted.

**Conclusion — the key fact the user's question turned on is now CONFIRMED, not just hypothesized**: on every cold boot (MCU reset), the bootloader polls its own USB hardware register, completely independently of whatever state the application region is in. If a USB stick with a valid `*.fw` file is present, it unconditionally runs the exact same flash-rewrite path as any official update — **whether or not the application has ever booted successfully**. Only if no device/file is found does it attempt the application jump. This means:
- A bricked/hung application (one that fails the SP-sanity check, or hangs for any other reason after booting) does **not** prevent the next cold boot's USB-update scan — that scan is pure bootloader logic, structurally incapable of depending on app state.
- An update interrupted mid-write (e.g. power loss during the sector 4–11 erase/program cycle) is recoverable the same way: power back on with the USB stick (containing a known-good `.fw`) in place, and the bootloader's write loop simply re-runs from the start (erase-then-write per sector, no resume state to get confused by).
- The practical recovery action is a **true power cycle** (actually removing and restoring power, e.g. unplugging from mains) — not merely pressing the front-panel "power"/standby button, since standby is application-controlled STOP-mode sleep (see the dedicated standby section below) and does **not** reset the MCU or re-run any of this bootloader logic. If the application is genuinely hung, the standby button itself may not respond (it's application code); a real power interruption is what forces a fresh reset back to the vector table and this polling sequence.
- This recovery path's own reliability is bounded by the same assumption any stock firmware update already depends on (the bootloader's hardware-poll/file-resolve/write-loop code must itself be functioning) — it is not a "no risk" guarantee, but it is the **same mechanism and same risk level as every official HK software update**, not a separate, weaker, unconfirmed path.
- **This specific `query-status` patch adds no new risk to this picture**: it modifies only `FUN_08044dc4` (a response-building function reached solely from the already-running network dispatcher) and a free-flash trampoline — neither address is anywhere near the vector table, stack-pointer-sanity value, or any boot/init code the bootloader's checks examine. The worst realistic failure mode for this patch, even if some edge case were missed, is a hang/crash of the network-dispatch task after the app has already fully booted — not a failure to boot, and not something that could prevent the USB-recovery path above from working.

## CONFIRMED CLOSED: all 3 remaining vector-table candidates are false positives (item 9)

Byte-dumped the context around each of the three previously-unverified scanner candidates (`vector-table-scan.log` / `final-sweep.log`):
- **`0x0800d050`** and **`0x080bbe54`**: both sit inside ordinary literal-pool/function-pointer data tables — consecutive, valid-looking code/RAM pointers that coincidentally pass the scanner's permissive "looks like a vector table" heuristic. ### CONFIRMED CLOSED: exact patch-hook byte offset for a new dispatcher command (item 11)

Full raw disassembly of the dispatcher's true tail (`FUN_08049d90`, `final-sweep.log`) pins down the function's real end and its final fallback arm:
- The function's last comparison arm runs `0x0804b00c`–`0x0804b018`: it loads a literal string pointer (`0x0804b128`), calls the `strcmp`-style comparator `FUN_08077c44`, then `cmp r0,#0; bne 0x0804b028`.

This requires changing only a handful of existing bytes (one branch target) plus adding new code entirely within already-confirmed unused flash — no relocation of any existing function.

## TCP/10025 XML service and internal status path

- `FUN_08044dc4` (`0x08044dc4`) assembles a response buffer from fixed strings and dynamic arguments. Its string references include the AVR171/AVR1710 HTTP header, XML opening/closing fragments, and the XML response prefix. The prefix contains the literal tag `<staus>`; its apparent spelling mismatch with `</status>` is present in the image and should not be silently corrected when documenting the wire protocol.
- `FUN_08049d90` (`0x08049d90`) is a command dispatcher. It calls the response builder and `FUN_0804541c` (`0x0804541c`) on multiple branches, alongside many command-specific handlers.
- **LIVE-CONFIRMED + CONCLUSIVELY EXPLAINED: `query-status` replies are real dispatcher output, but can never carry an actual value — this is a structural property of `FUN_08044dc4`, not a standby/network artifact.** A live retest of port 10025 while the device was normally powered on (not in standby) found all three ports (80, 8080, 10025) open, and sending `query-status`/`para=power` (and `source`/`volume`/`mute`) returned a response that was **not** a byte-for-byte echo this time: the `<name>` field was rewritten from `query-status` to `power` (etc.), and `Content-Length` was correctly recalculated for the new, shorter body — proof this really is `FUN_08049d90`/`FUN_08044dc4` actively parsing and replying, not a raw bounce. This exactly matches the dispatcher logic already resolved in `dispatcher-command-table.log` (`DAT_0804b104`→`'power'` branch, which evaluates the real state byte at `0x2001c030` and calls `FUN_08044dc4(DAT_0804b104, 0, &DAT_0804b038/"on"` or `&DAT_0804b03c/"off")`).
  - However, decompiling `FUN_08044dc4(param_1, param_2, param_3)` itself (`response-builder-trace.log`) shows the reply body is built by concatenating exactly five pieces: a fixed XML/`<staus><name>` prefix, **`param_1` only**, then three more fixed literals — resolved by direct byte-read to `'</name><zone>'`, `'</zone><para>'`, `'</para></status></common></avr></harman>'`. `param_2` and `param_3` are stored to stack locals (`uStack_2c`/`uStack_28`) but are **never referenced again** — they do not appear anywhere in the concatenated output. The reconstructed template, `...<name>{param_1}</name><zone></zone><para></para></status>...`, is byte-identical to every live `query-status` response captured (e.g. `<name>power</name><zone></zone><para></para></status>`).
  - **Conclusion**: regardless of the real, correctly-computed `"on"`/`"off"` (or source-name/volume) value the dispatcher passes as `param_3`, `FUN_08044dc4` structurally drops it before the reply is ever sent. Every `query-status` response over TCP:10025, in every power/standby state, will report the queried item's name but an always-empty `<zone>`/`<para>` — this is a deterministic, repeatable firmware characteristic (arguably a shipped bug) of V002.23's response formatter, confirmed by matching static decompilation to live bytes, not a timing, standby, or wrong-command issue. `FUN_0804541c` (also decompiled) is the separate send step — it just `strlen()`s and writes out whatever buffer `FUN_08044dc4` returned, with no further involvement in body content.

## Live standby/network behavior and CONFIRMED STOP-mode sleep architecture — option (a) BUILT, APPLIED, AND INDEPENDENTLY RE-VALIDATED

This section covers live, read-only network testing against the real device plus a full static trace of its answer: the one and only CPU sleep-entry routine in the image.

- **Live finding: port 10025 reachability is power-state-dependent.** While the device is powered on, 9/9 connection attempts across repeated checks were refused (consistent with the "outbound-POST-only, no listener" interpretation already documented above). With the user's confirmation that the device was freshly put into standby, a live retest found ports 80, 8080, **and** 10025 all accepting TCP connections — a state never seen while the device was on. A documented, non-mutating `heart-alive` POST sent to port 10025 in this state returned a response that was a **byte-for-byte echo of the request** (confirmed by exact byte comparison, down to trivial header whitespace), not the real `<harman><avr><common><staus>...</status>` dispatcher reply documented above — i.e., whatever answered was not `FUN_08049d90`. Minutes later, a follow-up check found the device **fully unreachable, including ICMP ping** ("Host is down"), while the user confirmed the physical display remained in ordinary blank standby (not hung). No "network standby"/"wake-on-LAN"/"eco"/"quick start" menu string exists anywhere in the image (confirmed by an extensive keyword string search) — whatever governs this is hardcoded behavior, not a user-facing setting.
- **CONFIRMED: the exact, sole CPU-sleep (STOP-mode) entry routine.** A targeted scan for the STM32F4 `PWR_CR`/`PWR_CSR` registers (`0x40007000`/`0x40007004`) and for `WFI`/`WFE` instructions anywhere in the image found exactly **one** hit for each, both in the same function: `FUN_08064de8`. Full raw disassembly confirms it: clears bits[1:0] of `PWR_CR` and ORs in a caller-supplied value (called with `1` → `LPDS=1, PDDS=0`, selecting STM32F4 **STOP mode**, not full Standby — SRAM/registers are retained, no reset needed to resume), sets Cortex-M `SCB->SCR` bit 2 (SLEEPDEEP) immediately before `WFI`/`WFE` (selected by a second parameter; called with `1` → `WFI`), then clears SLEEPDEEP again right after waking. This is textbook, correctly-implemented STM32 STOP-mode entry — not a hang, not a crash, not full power-off.
- **Confirmed pre-sleep/post-wake peripheral handling.** `FUN_08064de8`'s only caller, `FUN_08014a40`, wraps it as: pre-sleep GPIO reconfiguration (`FUN_08014aa0`, which switches ~5 GPIO pins to analog/low-leakage mode — a standard low-power prep step, pin identities/schematic role unknown), the STOP-mode call itself, then post-wake GPIO restore (`FUN_08014bec`, exact mirror with the mode bit reversed) and explicit peripheral-clock re-enable (`FUN_080657ba`, which calls the same RCC `AHB1ENR`/`APB1ENR`/`APB2ENR`-touching functions found in the clock-enable register scan). **This confirms that during STOP mode, all STM32 peripheral bus clocks — including whatever UART/SPI feeds the BridgeCo bridge chip — are gated off**, and are only explicitly restored in this post-wake routine.
- **CONFIRMED: STOP-mode entry is armed by a simple countdown, not a long human-scale timer.** `FUN_08014a40` is called from exactly one place in the main loop (`FUN_0801074c`), gated by: *"if a RAM counter byte (`0x2001c2ab`) is nonzero, decrement it; if it just reached zero, call `FUN_08014a40()`."* Every write site that arms this counter (at least 5 distinct call sites found, including the power-off-key handler) sets it to the literal value **7**. However, `FUN_0801074c` itself runs inside `FUN_08010184`, which in turn is called from an **unthrottled infinite loop with no fixed period or delay** (`do { FUN_08010184(); } while(true);`, confirmed at the tail of the top-level post-boot-init function `FUN_08064ede`) — there is no RTOS tick, no SysTick-driven scheduler slice, and no sleep/delay call between iterations. This means the "7-iteration" grace period is very likely **milliseconds**, not the multi-minute window actually observed live.
- **Synthesis — reconciling the fast STM32 sleep with the slower observed network behavior.** Since the STM32 itself appears to drop into STOP mode (and gate off its own UART/SPI clocks) within a very short time of a power-off request, the extended live-reachability window (ports still open shortly after standby) is best explained by the **separate BridgeCo CE2DM870 bridge chip** (already identified above as the host of the DLNA/UPnP stack and the most likely proxy for TCP:10025) continuing to run independently, on its own power/timeout schedule, for some additional time after the STM32 itself is already asleep — consistent with the observed reply being a raw echo (plausible as a BridgeCo-side fallback or a thin wake-time flush) rather than a real `FUN_08049d90` dispatcher reply (impossible if the STM32's UART to BridgeCo is clock-gated at that moment). The later complete unreachability (including ping) is then consistent with the BridgeCo chip's own, separate standby/power-down eventually completing. **The BridgeCo chip's own firmware is not part of this `.fw` image and its exact timeout cannot be determined by this project's static analysis.**
- **Feasibility assessment for "keep the network API alive during standby."** Making the real command dispatcher (`FUN_08049d90`) continuously available while the STM32 is asleep is **not** a small, additive patch like the already-designed item-11 dispatcher-command hook. It requires one of: **(a)** preventing STOP-mode entry entirely whenever network control should remain available (defeats the power-saving purpose of standby, and may keep other subsystems alive too unless carefully scoped — untested), or **(b)** identifying the specific GPIO/EXTI line carrying UART/SPI RX from the BridgeCo chip and configuring it as a wake-up source before entering STOP mode, so an incoming command itself wakes the STM32 on demand (the architecturally "correct" Wake-on-LAN-style design). Option (b) requires in-place modification of the core sleep-entry/wake sequence (`FUN_08014aa0`/`FUN_08064de8`/`FUN_08014bec`) rather than purely additive free-space code, and the exact GPIO/EXTI pin has not been identified — this is meaningfully higher-risk than the item-11 patch and has not been designed in detail.
- **Option (a) BUILT, APPLIED, AND INDEPENDENTLY RE-VALIDATED (new segment, explicit user request with due diligence).** Re-extracted `FUN_08064de8`'s raw bytes directly from the current patched `.fw` (not just the pristine original) and re-disassembled with `arm-none-eabi-objdump`, confirming the exact two sleep instructions: `wfi` (`0xbf30`) at `0x08064e0e` and `wfe` (`0xbf20`) at `0x08064e12`. Before patching, independently re-confirmed isolation at the raw-byte level (not just trusting the earlier Ghidra scan): scanned the **entire** 6 MiB image for the `PWR_CR` register literal (`0x40007000`) and found **exactly one** occurrence anywhere, belonging to this exact function — i.e. provably the only place in the firmware that configures the CPU for STOP mode, so no other sleep-entry path needs patching. Also scanned for an independent watchdog (IWDG, `0x40003000`); the one raw byte match found was at a non-2-byte-aligned offset surrounded by nonsense disassembly (a coincidental match inside a data region, not real code) — no watchdog dependency. Patched both `wfi`→`nop` (`0xbf00`) and `wfe`→`nop` in place — same-size, zero-trampoline, two single-instruction replacements; confirmed via `cmp -l` that **exactly 2 bytes changed in the entire 6 MiB file** (the WFI/WFE/NOP encodings share the same `0xbf` high byte, so only the low byte of each instruction differs), at precisely the two intended offsets, with no file-size change. Independently re-verified via a **completely fresh Ghidra re-import** (`AVRSleepPatchVerify.java`, `-loader BinaryLoader -loader-baseAddr 0x08000000`): the function now decompiles to `*PWR_CR = (*PWR_CR & ~3) | param_1; *SCB_SCR |= 4; *SCB_SCR &= ~4; return;` — i.e. it still configures `PWR_CR` and toggles `SCB->SCR`'s SLEEPDEEP bit exactly as before, but the actual halt instruction is gone entirely from the decompiled view (a NOP has no C-level effect), so the function returns immediately instead of ever halting the core clock. Function entry/exit boundaries (`0x08064de8`–`0x08064e23`) are unchanged. Everything else — the countdown-arm mechanism, the pre-sleep/post-wake GPIO reconfiguration, the post-wake peripheral-clock re-enable, and the separate `DAT_08019354`-gated amplifier/display power logic — is untouched, so the receiver should still visually/audibly appear to power off exactly as before; only the MCU's own clock-gating stops happening, keeping every peripheral bus (including whatever feeds the network-facing bridge chip) continuously clocked. Applied to `AVR1710_USB(V002_23)_patched.fw` (now also containing the query-status, version-bump, and CEC fixes) via `apply_sleep_disable_patch.py`, following the same verify-before-write/backup discipline as the prior two patches; backup saved as `AVR1710_USB(V002_23)_patched.fw.pre-sleep-disable-fix.bak`. **Residual uncertainty, stated plainly:** there is no schematic-level pin mapping to 100% rule out some other subtle effect of the CPU never truly halting beyond the expected/accepted trade-off (higher standby power draw/heat); this has not been tested on real hardware yet and should be live-verified after flashing (does TCP:10025 actually stay reachable once the receiver is put into standby?).

## HDMI/CEC state reporting

- Inventory string references map `CEC: Sending report power status=%x` to `FUN_0804b304` and `CEC: Sending audio status=%x` to `FUN_0804b56e`; both are called by `FUN_0804d134`.
- `FUN_0804b304` constructs a CEC frame whose opcode byte is `0x90` (report power status) and passes it to the frame-send path. `FUN_0804b56e` constructs opcode `0x7a` (report audio status), obtains its payload from `FUN_0802d174`, and sends it through the same low-level path. `FUN_0804d134` (the CEC dispatcher itself) is a clean 32-bit pending-flags bitmask drain loop with no direct reference to the XML service's status byte anywhere in its own body.
- **CONFIRMED — item 8 closed: CEC and the TCP/10025 XML service are bridged via one shared system-state region in RAM, not via direct cross-calls.** Decompiling `FUN_0802d174` (the CEC audio-status value source) shows it reads three RAM bytes through literal-pool pointers: a mute/mode flag, a standby-like flag, and a 0–180-scale volume value (mapped to a 0–100 percentage, with special-cased 100%/1% values) — clearly the AVR's real, shared volume/mute state. Resolving those three pointers by direct byte-read gives **`0x2001c038`, `0x2001c1dc`, and `0x2001c290`** — all inside the same `0x2001c0xx` RAM region as the XML service's own power-state byte, **`0x2001c030`**, found earlier (the CEC mute-flag byte sits just 8 bytes after the XML power-state byte). This is a shared, central "AVR system state" memory arena: the CEC subsystem and the TCP/10025 XML dispatcher both read/write fields of the *same* region rather than calling into each other. A power/volume/mute change made via one interface (XML command or HDMI-CEC) is therefore reflected in the other's status reads through this common backing store, not through any direct function call — which also explains why none of the three originally-examined CEC report functions reference `0x2001c030` directly: the bridge is at the memory-layout level, one level removed from the report-formatting functions themselves.
- Other inventory strings confirm CEC route/active-source handling, ARC, system-audio mode, and CEC standby processing. Their full state and task relationships remain to be mapped (not required to close item 8).

## HDMI/CEC deep review — one confirmed bug found and FIXED (Active Source validation bypass), rest of the stack looks sound

This is a licensed-looking Silicon Image ("Sii"-prefixed) reference CEC stack — far larger than the 3 functions examined earlier, covering remote-control passthrough, System Audio Mode (broadcast + directly-addressed), routing/active-source, physical-address reporting/defaulting, vendor ID, OSD name, CEC version, and standby handling.

**TX side (`FUN_0804d134`, the pending-flags dispatcher) — reviewed, no bugs found.** Decompiled all ~18 remaining send-handler functions referenced from its 32-bit bit-drain loop (`FUN_0804b91a`, `FUN_0804b28c` Give Vendor ID, `FUN_0804b400`/`FUN_0804b2c2` Report Physical Address/Report Vendor ID, `FUN_0804b452`, `FUN_0804b948`, `FUN_0804b4b2`, `FUN_0804b5ba`, `FUN_0804b61a` Set System Audio Mode Broadcast, `FUN_0804b8a0`/`FUN_0804b75e`, `FUN_0804b7b6`, `FUN_0804b6a4` Set System Audio Mode Directly, `FUN_0804b3bc`, `FUN_0804b352` Set OSD Name, `FUN_0804b536`, `FUN_0804b506`, `FUN_0804b8e8`). Each builds a CEC frame matching its opcode's real spec layout (header/opcode/operand byte counts all line up with `FUN_0807bf50(ptr,len)`'s length argument). One early lead — `in_r3` appearing as an "uninitialized" value in two functions — turned out to be decompiler noise: those bytes are written to stack positions beyond the actual transmitted length and are never sent, confirmed by checking the `len` argument at each call site. No repeat of the query-status "compute but drop" pattern on this side.

**RX side — found a real, assembly-confirmed bug.** `FUN_0809b3fc` handles 5 incoming opcodes: `<Standby>` (0x36), `<Routing Change>` (0x80), `<Routing Information>` (0x81), `<Active Source>` (0x82), `<Set Stream Path>` (0x86). Each branch checks an operand-length byte (`param_1[0x14]`) before trusting the operand bytes — **except `<Active Source>` (0x82)**:
```c
if (sVar3 == 0x82) {
    if (param_1[0x14] != 2) {
        FUN_0809b394(DAT_0809b678);   // reports "wrong length" error...
    }
    FUN_0808cde0(*param_1 >> 4, CONCAT11(param_1[4],param_1[5]));  // ...but runs anyway, unconditionally
}
```
Confirmed at the disassembly level (`cec-asm-check.log`): `beq 0x0809b4c4` skips the error-report call when the length is correct, but the "wrong length" path falls straight through into the exact same `ldrb r0,[r4,#0x4]` / `FUN_0808cde0` call — there is no `bne`-to-skip or early return after the error report, unlike the other 4 opcodes in the same function (which all use a true if/else that never executes the real action on the error path). This is the identical "validate but don't gate" defect class already fixed in the XML `query-status` handler, this time in the CEC receive path.

**Impact, characterized precisely (not overstated):** `FUN_0808cde0` only writes the parsed (possibly garbage, if length was wrong) source logical address + physical address into the shared "last known active source" state slot (offset `0x33`/`0x34` of the CEC state struct) and resets a timeout counter — it does **not** itself trigger an input switch. The actual input-switch path, `<Set Stream Path>` (0x86) → `FUN_0809b3a4` (PA→port lookup) → `FUN_0808c9a2` (switch), is correctly length-gated and **not** affected. So the confirmed effect is limited to corrupting an internal tracking value when a CEC peer sends a non-conformant (wrong operand count) `<Active Source>` message — not a guaranteed spurious input-switch, though exactly the class of corner case that produces classic "my receiver randomly changed input" CEC flakiness complaints, since real-world CEC peers (especially cheaper TVs/STBs) are known to occasionally send off-spec frames.
- **BUILT, APPLIED, AND INDEPENDENTLY RE-VALIDATED.** Same trampoline technique as the query-status fix: patch site `0x0809b4bc` (4 bytes: `beq 0x0809b4c4` + `ldr r0,[0x0809b678]`) replaced with `b.w 0x080c89f8` (exact-length swap); a new 22-byte trampoline at `0x080c89f8` (free space immediately adjacent to the existing query-status trampoline) re-tests the same condition-flags, then on the error path reports the error exactly as before but now branches to `0x0809b4d8` (the shared tail) **instead of** falling into `FUN_0808cde0` — skipping the vulnerable call entirely. The valid-length (`==2`) path is byte-for-byte unchanged in effect (one extra unconditional jump through the trampoline's first instruction). All bytes were produced by Ghidra's own Assembler (`AVRCecPatchBuild.java` / `cec-patch-build.log`), applied via `apply_cec_patch.py` with the same verify-before-write/size-check/backup discipline as prior patches, and **independently re-confirmed via a completely fresh Ghidra import + re-analysis** (`AVRCecPatchVerify.java` / `cec-patch-verify.log`) — the fresh auto-decompile now shows a proper `if (param_1[0x14] == 2) { FUN_0808cde0(...); } else { FUN_0809b394(...); }`, matching the pattern used by the function's other opcodes. Byte-diff confirms exactly 2 new changed ranges (4 + 22 bytes, 26 bytes total) and zero file-size change. New cumulative deliverable hash: sha256 `df17e021f450017036e5e2656c3c7008dcff02433f48aabcd78ea0e89ddb6bd7` (4 changed ranges total across all 3 patches now applied: query-status fix, version bump, CEC fix — 101 bytes changed overall out of 6,291,456). **Not live-tested** (unlike the query-status fix, this isn't reachable over the network API — it requires a real CEC-capable TV/source sending a malformed `<Active Source>` frame, which isn't practical to trigger on demand); confidence instead rests on the assembly-level before/after comparison and the independent fresh-reimport re-decompile.

Our two prior patches modified `FUN_0809b3fc`, a function that is never reached, so they could not have had any effect — fully consistent with both negative live tests. The actual bug must be **inside `FUN_080192e2`'s own branch-gating** (countdown `*DAT_0801962c` + the two other state bits documented above) choosing its full-shutdown branch when reached via this path, or in exactly what state `gateA`/`gateB` (`DAT_0802da94`, `DAT_0802de8c`) are in at the moment CEC delivers `<Standby>` versus when a button/IR event does. This is a materially different, more precisely-targeted lead than anything tested so far, but it has **not yet been live-tested** and the overconfidence of the last round (claiming a fix was "proven" when it was never actually exercised) should not be repeated — next step is to fully trace `FUN_080192e2`'s 3-way branch and the `gateA`/`gateB` state producers before proposing any new patch, and to be explicit with the user that this is a new hypothesis, not a confirmed fix.

## CEC-standby regression after patch #4 — full causal-chain analysis (conclusive on code paths, inconclusive on live timing)

**Reported symptom**: after patch #4 (no-op trampoline) + volmute fix flashed together, a CEC-triggered standby shows the "device switched off" message but the receiver does **not** power down. If that has happened, a *subsequent* physical power-button press then causes a **full hard shutdown** (not the normal sleep). A button press with no prior CEC event still just sleeps normally.

**Method**: full decompile of `FUN_0802d230` (the real shared power-request dispatcher for both CEC `param_1==4` and button/IR `param_1==0x20`), full decompile of `FUN_08019378` (corrected from a prior-segment error — it is a state-*reset* function, not a countdown-arming one), precise raw-disassembly (not decompiler idiom, to avoid sign-trick misreads) of the tick dispatcher `FUN_08011910`'s handling of both deferred countdown cells, and an exhaustive whole-firmware literal-pool scan for every writer of RAM `0x2001c030` (103 raw candidates, de-duplicated to 69 unique store sites, each bit-op precisely classified).

**Confirmed, by direct evidence (not inference):**
1. `FUN_0802d230`'s CEC (`param_1==4`) and button (`param_1==0x20`) branches are **byte-for-byte identical** except in one case: when gateA (bit 1 of RAM `0x2001c030`) is false, CEC does nothing at all, while button instead calls `FUN_08019272()` directly (wrapped in a protective flag CEC's path never sets). This is the *only* code-path asymmetry between CEC and button anywhere in this dispatcher.
2. When gateA is true: gateB (bit 0 of RAM `0x2001c09c`) selects between (a) gateB-true → immediate `FUN_080192e2()` call (the path neutered safe by patches #1–#4), or (b) gateB-false → **arms a second, previously-unpatched deferred countdown, `*0x2001c2b5 = 100`**.
3. The tick dispatcher re-checks bit 1 of `0x2001c030` **at the moment the `0x2001c2b5` countdown reaches 0** (not when it was armed): if set, calls the now-neutered-safe `FUN_080192e2()`; if clear, calls `FUN_08019638()` (full/hard shutdown) **directly and unconditionally — a 5th call site, structurally identical in role to the 3 patched in rounds 1-4, that no prior patch has ever touched.**
4. RAM `0x2001c030` bit 1 is written at only 6 confirmed places firmware-wide (of 69 total store sites to that byte, only 6 touch bit 1 specifically — all others manipulate unrelated bits 0/3/4/5/7 of the same packed byte):
